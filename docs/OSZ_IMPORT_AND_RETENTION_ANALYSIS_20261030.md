# osu! 与 osu!lazer 的 OSZ 导入及原包保留方案

分析日期：2026-10-30。

实施状态：本报告保留分析时的现状和建议。随后已实现可选 DLL 导入接口、播放列表入口及工作副本流程；实际已完成内容、引用保护和测试边界见 [实施记录](OSZ_IMPORT_IMPLEMENTATION_20261030.md)。

可以为 TTPlayer 增加“导入后保留原 OSZ”选项，并保证勾选时原包不会被本次导入流程消费。关键是始终把完整、独立的工作副本交给游戏，原包留在游戏导入目录之外。stable 和 lazer 当前都存在移动或删除传入 OSZ 的逻辑，不能直接把原路径传给游戏，再用一个播放器设置阻止游戏清理。

“取消保留”应解释为**确认导入成功后清理原包**。游戏启动、IPC 投递成功和副本消失都不构成完整导入成功证明；无法确认时应留下原包及任务记录。开始本分析时，播放器尚未实现游戏导入或这一保留选项。

## 2 stable 的导入流程

### 2.1 外部打开和拖放

文件类型判断方法 `0x06002D1A` 将 `osz` 分到类型 1。游戏的外部文件处理方法 `0x06001DCC` 接收路径数组，取文件名并组合成实际 `Songs` 目录下的目标路径，再调用 `0x06002D12`。

该辅助方法的核心操作是 `File.Move(source, destination)`，调用方传入覆盖标志。源和目标为同一路径时直接返回；否则先尝试清理目标，再移动源包。成功后设置待导入标志，随后进入曲包处理。因而外部原包可能在真正解包之前就从原位置消失。

拖放、启动参数及已有实例的 IPC 最终可进入同一文件处理分支。拖放界面虽然返回 `DragDropEffects.Copy`，OSZ 分支仍执行上述移动，不能根据鼠标拖放提示判断原文件会保留。

如果游戏正在游玩或编辑，方法中存在“进入选曲界面完成导入”的提示分支。向已有游戏投递文件后必须允许等待，不能给一个固定短延时后就报告安装完成。

证据位置：私有 `stable-game.cs:346`、`:2483`、`:2537`、`:2554`；`stable-files.cs:298`、`:616`；`stable-ipc.cs:365`。

### 2.2 解包和清理

导入方法 `0x060027EA` 枚举 `Songs` 根目录的文件，发现 OSZ 后进行以下处理：

1. 从包名生成谱面目录名，处理 `-novid` 和过长路径。
2. 将包解压至临时目录，处理解包错误及所需文件检查。
3. 必要时清除包文件的只读属性。
4. 将解压目录移动或合并到 `Songs/<谱面目录>`，登记目录供曲库处理。
5. 调用 `0x06002D16` 清理 OSZ。

清理方法先尝试 `File.Delete`；删除失败时还会尝试移入隐藏的 `_cleanup` 目录。异常处理方法 `0x060027ED` 则尝试把出错包移到 `Songs/Failed`。

因此，“输入路径已经不存在”可能是已移入 Songs、移入 Failed、正常删除或转入清理目录，不能独立证明谱面已经成功识别。将原包设成只读也不能作为保留方案，因为导入代码会主动清除此属性。

证据位置：私有 `stable-import.cs:150`、`:185`、`:209`、`:219`、`:342`；`stable-files.cs:358`。

官方文档同时确认 stable 支持打开 OSZ，或者将其放入 Songs 后由游戏处理；必要时在选曲界面按 F5 重扫。该文档只用于确认公开入口，以上删除细节来自本机二进制。[osu! 安装与添加谱面](https://osu.ppy.sh/wiki/en/Client/Installation)

### 2.3 对保留选项的影响

原包应留在普通下载目录或独立归档目录。若原包本来就在 `Songs` 根目录，游戏自身的扫描也可能消费它；在这种情况下只能先另存到导入扫描范围之外，保证保留一份原始 OSZ，不能承诺游戏运行后原位置始终不变。

向 stable 投递副本还要处理 `Songs` 根下同名待导入包：原版移动分支带覆盖行为。任务目录唯一并不足以解决这个冲突，因为游戏会再次提取文件名。应串行投递并检查同名待导入文件；异内容冲突不得静默覆盖。必要时给工作副本编号，并记录这会影响 stable 的目标目录命名。

## 3 lazer 的导入流程

### 3.1 入口共用导入器

命令行、拖放、游戏内文件导入界面最终分发到 `BeatmapImporter`。它接受 `.osz` 和 `.olz`，通过 ZIP reader 读取包内容，再由 `RealmArchiveModelImporter` 建立谱面集合。

主要源码位置，以本地 `D:/Git/OSU/osu` 为根：

| 位置 | 行为 |
| --- | --- |
| `osu.Game/OsuGame.cs:377`、`:1418` | 拖放和启动路径进入导入分发 |
| `osu.Game/Screens/Import/FileImportScreen.cs:172` | 游戏内选择文件或目录导入 |
| `osu.Game/Database/ImportTask.cs:47` | 打开包并创建 archive reader |
| `osu.Game/Database/RealmArchiveModelImporter.cs:254` | 导入、关闭 reader、随后决定是否删除传入包 |
| `osu.Game/Beatmaps/BeatmapImporter.cs:165` | 根据扩展名决定 OSZ 应删除 |
| `osu.Game/Database/ImportTask.cs:77` | 对传入路径执行删除 |

只有获得非空导入模型后，正常流程才执行包删除。删除异常被记录，但不撤销已经成功的模型导入，所以“入库成功”和“源文件删除成功”需要分别记录。[安装版本对应的统一导入器](https://github.com/ppy/osu/blob/9a10d935b05a3b896f4bd811d620f2023331db93/osu.Game/Database/RealmArchiveModelImporter.cs#L254)

### 3.2 保存的是成员和索引

`RealmFileStore.Add` 对每个成员计算 SHA-256，存入 `files` 内容存储；相同内容可复用。Realm 中的具名引用保存“原相对文件名 → 内容哈希”关系，谱面集合再引用这些成员。

导入器还会去除公共目录前缀、规范化分隔符、拒绝路径穿越和忽略大小写后重名。创建难度时只处理规范化后的顶层 `.osu`；空谱面、重复内容或缺少规则集的难度可能被跳过。

这并不是把原 ZIP 整体保存起来。以后导出 OSZ 可以恢复成员和路径，但不保证原来的压缩方法、压缩级别、成员顺序、ZIP 附加字段或整体 SHA 相同。当前 TTPlayer 导出使用 Stored，而上述 neu 样本使用 Deflate，已经说明“重新导出”不能代替“保留原始包”。

源码：`osu.Game/Database/RealmFileStore.cs:44`、`RealmArchiveModelImporter.cs:373`、`:519`、`osu.Game/Beatmaps/BeatmapImporter.cs:366`。当前 DLL 导出方式见 [完整谱面包导出](OSZ_EXPORT_20261027.md)。

### 3.3 重复导入和取消

| 情况 | 安装版源码行为 | 播放器应如何处理 |
| --- | --- | --- |
| 成功新建或更新 | 尝试删除传入 OSZ | 仍须验证目标集合及成员 |
| 重复包复用既有模型 | 返回非空模型，仍可能删除传入 OSZ | 可记为“已存在且校验通过”，不能只看集合 ID |
| 无有效谱面或事务失败 | 通常不会进入删除分支 | 保留原包并记录失败 |
| 开始前取消 | token 检查可阻止导入 | 清理自己尚未交付的副本，原件不动 |
| 复制或事务开始后取消 | 同步阶段未持续检查 token，可能仍完成并删除传入包 | 已交付任务只能停止本方等待，不能承诺撤回游戏内操作 |
| 删除传入包失败 | 记录错误，模型仍可成功返回 | 区分入库状态和清理状态 |

普通导入和批量快速复用都可能返回已有模型。事务失败后也可能留下尚未被引用的内容文件，等待游戏清理；不能仅以 `files/<hash>` 存在作为入库证明。

### 3.4 没有可直接调用的保留参数

所检查的 `ImportParameters` 只有 `Batch`、`PreferHardLinks` 和 `ImportImmediately`；IPC 消息只有 `Path`。没有找到可由外部调用的 `keep` 或 `preserve` 参数。

`ArchiveImportIPCChannel` 收到请求后安排异步导入并立即回复；桌面程序等待 IPC 的 3 秒超时是投递阶段，不是完整导入超时。新启动的游戏进程也可能只是把请求转交给已有实例，因此其退出码不能作为导入成功回执。

源码：`osu.Game/Database/ImportParameters.cs:6`、`osu.Game/IPC/ArchiveImportIPCChannel.cs:24`、`osu.Desktop/Program.cs:161`。

从 stable 导入已解压曲库是另一条路径，会枚举谱面目录并可优先使用硬链接，不删除 stable 原目录。这与把 OSZ 传给 lazer 不同，不能据此推断 OSZ 会保留。所检查的路径中未发现与 stable 相同的 Songs 根目录 OSZ 扫描入口；不要将 OSZ 直接放入 lazer 的 `files`，那样不会建立有效 Realm 索引。

## 5 推荐的保留和清理规则

### 5.1 共用工作副本流程

1. 校验所选目标是配置的 stable 或 lazer 程序，识别实际存储路径。
2. 在后台读取 OSZ 目录，核验成员路径及谱面清单，登记原文件身份、大小和 SHA-256。
3. 创建任务专用目录，以实际文件复制产生工作包，写完刷新、关闭并核对副本完整性，再提交给游戏。复制及校验提供进度和取消，不把整个包装入内存。
4. 明确启动配置的 EXE，并将正确引用的副本绝对路径作为参数。不要依赖系统 `.osz` 文件关联，也不要构造 shell 命令。
5. 游戏处理工作副本；播放器持久保存任务状态，等待后续只读核验。
6. 确认后刷新专用曲库列表，再按保留和引用规则处理原包。

使用物理副本，不用硬链接或符号链接代替。原包与游戏工作文件的内容及属性应相互独立。若同时导入两个游戏，应分别准备两份副本；不能让两个游戏竞争同一个可被删除的文件。

stable 的副本宜放在与 Songs 相同卷、但不会被自动扫描的任务目录，减少其移动路径的兼容性问题；还需按第 2.3 节处理 Songs 根下的同名待导入包。lazer 的任务目录应位于内容存储之外。

### 5.2 勾选保留

原包始终不作为游戏输入，不执行源包清理。游戏消费工作副本，不影响归档原件。这可以保证本导入流程不会删除、移动或重写保留的 OSZ，且保留的是相同字节的原始容器。

原路径处于游戏扫描目录时，先生成目录外的保留副本，并明确显示归档位置。保留选项不依赖游戏内部增加设置。

### 5.3 取消保留

仍使用工作副本，不提前把原件交给游戏消费。只有以下条件同时满足，才清理原包：

- 所有本次选择的目标均已确认包含所需集合、难度及资源；若一个目标失败或尚未确认，则保留。
- 原包没有被任意播放列表、当前播放或其他待处理任务引用。
- 删除前核实原路径仍对应登记的文件身份和内容，避免删除后来被替换的同名文件。

清理结果独立记录。建议采用回收站方式；不支持可撤销删除或文件被占用时，保留并显示“导入完成，原包未清理”，不偷偷降级为永久删除。

没有足够证据时显示“已交给游戏，尚未确认”，保留包和任务记录。用户取消等待也不意味着游戏撤销了已开始的导入，不应关闭游戏或删除仍可能被读取的工作包。

### 5.4 播放列表引用必须单独处理

当前 OSZ 条目使用 `原OSZ绝对路径|包内音频路径`，原包还可能承担背景图来源。仅删除 OSZ 会造成下次播放或读取背景失败，当前曲目因缓存仍有声音不能证明安全。

首版建议发现引用就保留原包，并说明仍被播放器使用。若以后增加引用迁移，必须按集合、成员名和内容哈希匹配对应音频及背景，处理一个包多个音频的情况，并原子更新全部相关列表；不能仅凭曲名、集合 ID 或一个音频哈希替换路径。

## 6 如何确认导入完成

导入核验应以“这一包的内容是否已进入所选曲库”为目标，不能只数歌曲或查同名目录。

| 目标 | 内容核验 | 游戏识别核验 |
| --- | --- | --- |
| stable | 定位目标谱面目录，逐项验证原相对路径和成员内容；至少包括所有需要保留的 `.osu`、音频、图片、音效、脚本和视频 | 核对游戏曲库索引已接纳相应难度；文件解包完成与游戏识别完成分开记录。索引更新有延迟时继续等待 |
| lazer | 读取一致的只读 Realm 快照，定位未删除的集合，核对 `Files` 名称／哈希和实际内容文件；遵循导入器的路径规范化规则 | 核对集合关联的有效难度，排除 `DeletePending`；单独的孤立哈希文件不算成功 |

集合 ID 和标题只用于缩小查找范围；完整包、无视频包、mini 包可能同 ID、同文件名而内容不同。重复导入时若目标完整匹配，可以记为“已存在且验证通过”。若原包有被游戏拒绝的难度、只导入部分内容或数据库模式无法解析，则不得假定全包成功并自动清理原件。

现有 native 曲库枚举和导出规划能减少实现工作，但还没有完整的导入结果核验器。对不修改的原版游戏，不能承诺任何版本、任何包都能立即拿到最终成功回执；可以承诺无法确认时不自动清理原包。不要直接修改 `osu!.db` 或 `client.realm` 来制造成功状态。

## 7 建议的接入顺序

1. **独立导入接口和保留模式。** 在 `ttp_osu` 增加独立查询入口，使用可检查 `size` 和 ABI 的结构，保留现有 1 至 6 号接口。先完成目标识别、后台工作副本、明确 EXE 投递和持久任务记录。宿主只管理 UI、设置和播放器引用。
2. **结果核验和强制刷新。** 增加 stable、lazer 各自的完成判定，区分“已提交”“等待游戏”“内容已落盘”“已确认”“失败”“无法确认”。导入完成使相应专用列表缓存失效，再重新扫描。
3. **取消保留时的清理。** 在核验和引用保护可用后，启用导入成功后的可撤销清理，更新下载记录，不再将已清理路径当作可播放文件。
4. **入口和自动导入。** 下载完成菜单增加“导入 osu!”和“导入 osu!lazer”，独立导入对话框提供“导入后保留原 OSZ”，建议默认勾选。自动导入设为单独配置，默认关闭；仅下载、直接播放 OSZ 均不隐式安装游戏。
5. **批量和双目标。** 以包为任务单位，持久记录每个目标的结果，支持重复请求去重、重名工作包、暂停等待和重启恢复。插件缺失或导入接口不可用时隐藏相应入口。

以上为设计建议，未更改当前默认设置。保留开关和“下载后自动导入到哪个游戏”应分开，避免一次关闭保留就意外改变下载或播放行为。

## 8 实施后的验证矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| stable／lazer 未启动和已启动 | 都交付到明确所选目标；投递完成不冒充导入完成 |
| 保留开启 | 导入前后原包身份、长度及 SHA-256 不变；目标成员完整 |
| 保留关闭 | 只在完整核验、无引用、原件身份匹配后清理；失败或未知不清理 |
| neu 多音频样本 | 4 个难度和 11 个成员关联正确，3 个音频不合并丢失 |
| 双目标、批量、重复导入 | 副本独立；重复包可验证已有内容；一个目标失败时不提前清理源包 |
| 同 ID 不同版本或无视频包 | 不凭 ID、标题、单个音频或副本消失判断全包成功 |
| 正在播放／编辑／暂停导入 | 保持等待，不误报超时失败后清理，也不关闭游戏 |
| 损坏 ZIP、无有效谱面、缺失音频、非法相对路径 | 明确失败，原件保留；不静默生成部分成功状态 |
| 磁盘空间不足、工作包同名、跨卷、中文及长路径 | 可恢复失败；不覆盖其他待导入包或原始文件 |
| 原包在 Songs 根目录 | 先建立扫描目录外的保留副本，显示正确归档位置 |
| 玩家取消等待、播放器或游戏崩溃、重启 | 持久任务可恢复，仍待游戏读取的副本不被抢先清理 |
| 原路径被同名文件替换 | 文件身份不符时不删除新文件 |
| OSZ 已加列表或正在播放 | 保留源包或完成经验证的引用迁移，音频和背景不失效 |
| 导入后专用列表 | 同路径强制刷新，新的歌曲信息和背景可见 |

实际游戏运行测试只在该游戏版本支持的系统进行。播放器／DLL 的 XP、Win7 兼容检查不能替代现代 lazer 的运行条件，也不应把在旧系统上正确显示“不支持此目标程序”计作游戏导入成功。
